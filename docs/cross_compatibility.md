# Cross-compatibility: the pinned contract, the guard, the registry

PoRobotTrain is one of several Po apps whose policies are meant to be interchangeable. This file records
the three pieces that make that checkable here. The rules themselves live in `PoPunkouterSoftware/docs/unite/RULES.md`;
this is the local implementation and its current state.

## 1. `contracts.lock.json` — the pin

A copy of the numbers that must not drift: `n_obs`, `n_action`, `control_dt`, `decimation`, `timestep`,
the MuJoCo version, the three contract hashes, and the list of **legacy interfaces** that already exist
in the wild.

It carries enough for CI to check shapes without `PoPunkouterSoftware/docs/unite` on disk, which matters because
`global/` is not a repo and never appears in a fresh clone.

```powershell
.venv/Scripts/python.exe scripts/pin_contract.py --check   # exit 1 when the pin is stale
.venv/Scripts/python.exe scripts/pin_contract.py           # re-pin (a deliberate act)
```

Re-pinning is a breaking change: a changed `interface_sha256` invalidates every policy trained against
the old one.

## 2. `RobotControl/configs/contract.py` — the one source

Everything that needs an interface number reads it from here instead of hard-coding it.

```python
from robotcontrol.configs import contract as C

c = C.load()                    # 131 / 28, 50 Hz, 4-step decimation
c.assert_io(env.num_obs, env.num_actions)   # raises ContractMismatch on a wrong width
c.describe_io(23, 7)            # "legacy"
c.role_of("left_hip_pitch_joint")           # "hip_pitch_l"  (needs PoPunkouterSoftware/docs/unite present)
```

Two modes: **lock-only** (always available, used by CI) and **full** (adds roles, joint table, motor
slots when `PoPunkouterSoftware/docs/unite/creatures/unitree_r1_a5/contract.json` is present, and refuses to load if its
hashes disagree with the lock).

## 3. `RobotControl/training/policy_guard.py` — the gate

Called at the end of every export (`export_level0.py`, `train_head_skill.py`). It shells out to
`PoPunkouterSoftware/docs/unite/tools/verify_policy.py` and classifies the result:

| Result | Meaning | Behaviour |
|---|---|---|
| **conforming** | 131 / 28, hashes line up | pass, optionally write the sidecar |
| **legacy** | matches a recorded legacy interface | **export allowed**, logged as non-portable |
| **foreign** | neither | **abort** — a new interface nobody signed off on |

`UNITE_STRICT=1` turns legacy into an abort. The runtime prerequisite is now met — the twin feeds 131 and
drives 28 roles (section 5) — so flip it when the next policy is retrained on the role interface, knowing
it will then stop the grandfathered Level 0 and head-skill exports on purpose.

If `PoPunkouterSoftware/docs/unite` is absent (CI, fresh clone) the guard prints **NOT VERIFIED** and continues; the lock
still pins the shapes, so nothing is silently unguarded.

## 4. `agents/registry.json` — what exists today

Generated by `scripts/agent_registry.py`, keyed by `policy_sha256` so duplicate copies collapse.

```
.venv/Scripts/python.exe scripts/agent_registry.py --check
```

Current state (2026-11-28): **17 tracked files, 12 distinct policies, 0 conforming, 12 legacy.** The
registry counts git-tracked `.onnx` only, so it reads the same locally and in CI.

| policy | shape | legacy interface |
|---|---|---|
| `r1_level0_upperbody` (+ web twin copy) | 23 / 7 | `r1_level0_upperbody` |
| `look_at`, `glance_around`, `hold_centre` (v1) | 9 / 2 | `r1_head_skill` |
| `nod_yes`, `shake_no` (v1) | 6 / 1 | `r1_head_skill_single` |
| all five head skills **v2** | 131 / 28 | `unite_131_28@526e01aaf5153f7f` |
| walk sandbox (not in this repo) | 83 / 24 | `r1_level2_velocity` |

The v1 and Level 0 policies carry normalisation **inside** the ONNX graph, an R9 violation, so they can
only be retrained, never ported.

The v2 head skills are the right shape but the **wrong layout**. They were exported on 2026-11-27
against the retired `GLOBAL/rl_training/standards/unite` contract (`526e01aa`: root velocity 0..2,
gravity 6..8, joints from 9). The lock was re-pinned on 2026-11-28 to
`PoPunkouterSoftware/docs/unite` (`94377eba`: joints from 0). The registry detects this by the
`interface_sha256` in each `policy.unite.json`, not by shape. They keep running on the robot through
`behaviours/head_skills.pack_unite_obs`, which still writes the old layout. `train_head_skill --portable`
is disabled until that packer is rebuilt on `execution/role_interface.py`. A same-shape export from the
old packer would pass the shape-only guard while meaning something else.

## 5. `RobotControl/execution/role_interface.py` — the runtime that consumes the interface

The 131-float builder and the 28-role action map, in one module, reading every number from the pinned
contract. `PolicyRunner` selects it automatically when the ONNX is exactly `contract.n_obs -> n_action`
**and** a sidecar beside it matches; otherwise the deploy.yaml `ObservationBuilder` path is used exactly
as before, which is what every grandfathered policy needs.

| Piece | What it does | Rule |
|---|---|---|
| `RoleObs.build` | nine contract slots, role order, masked roles exactly 0, `role_mask` + `morphology_onehot` | R6/R8 |
| `RoleActionMap.targets` | `clip(default + a*action_scale, soft_lo, soft_hi)`, masked roles PD-held | R7 |
| `RoleActionMap.kp/kd` | per-joint gains from the contract, not from `deploy.yaml` | layer 6 |
| `sidecar_problems` | refuses a policy whose hashes disagree with the contract | R10/R14 |
| `for_policy` | `None` for a legacy shape, `RoleInterface` for a conforming one, raise for a stale one | R13/R22 |

Evidence, both runnable today:

```powershell
.venv/Scripts/python.exe -m pytest RobotControl/tests/test_role_interface.py -q   # 12 passed, incl. golden parity
.venv/Scripts/python.exe -m robotcontrol.main_runner --target sim --command-mode zero --duration 2 `
    --no-realtime --no-log --policy ..\global\UNITE\runs\ppo-r1-edu-stand `
    --deploy RobotControl\models\r1_role_stand\deploy.yaml
```

A fresh clone has no `global/` folder, so the module returns `None` in lock-only mode and the tests skip
rather than inventing a layout. The golden file is the authority; this builder is one implementation that
must reproduce it, not a copy of the reference.

## What is still missing

- **`PoPunkouterSoftware/docs/unite/tools/check_cross_app.py` lists this repo as the first app that can produce the 131
  floats.** It scans for a builder that names all nine slots; `RobotControl/execution/role_interface.py`
  does, and `tests/test_role_interface.py` proves it against `golden_role_obs.npz` to 1e-5.
- **The conforming example lives in `PoPunkouterSoftware/docs/unite/runs/ppo-r1-edu-stand`**, not in this repo, and is run
  with `--deploy RobotControl/models/r1_role_stand/deploy.yaml`. It is a balance seed, not a walking
  policy; its behaviour is reported beside its motor command so it is not mistaken for one.
- **No conforming policy is in `agents/registry.json` yet**, because none is deployed from this repo's
  `models/` folder. Nothing promotes the example to the robot without the `deploy.json` gate.

Order of work is in the RULES.md §5 sequence and was agreed here: Parts 1 and 5 (this file), then the
guard in the export path (done), then the twin, then one end-to-end head skill.
